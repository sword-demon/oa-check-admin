## Context

当前审批模板能力已经具备模板列表、BPMN 设计器、节点配置、模板发布和 Flowable 部署链路，但模板创建仍偏工程化：管理员需要理解 BPMN XML，表单配置也主要是 JSON 文本。目标用户更接近后台管理员或业务配置人员，他们需要像钉钉审批一样，在一个设计界面内完成“表单字段 + 审批流程 + 发布”的闭环。

现有核心链路如下：

```text
审批模板列表
  -> 创建/编辑 biz_process_template
  -> 设计器保存 bpmn_xml + biz_process_node_config
  -> 发布 published_bpmn_xml
  -> Flowable 部署流程定义
  -> 审批实例按模板发起
```

本变更在现有链路上补齐动态表单构建和更业务化的流程设计体验，不引入新的工作流引擎，不绕开 Flowable。

## Goals / Non-Goals

**Goals:**

- 提供新建审批模板向导：基础信息、表单设计、流程设计、预览发布。
- 将表单 schema 作为模板的一等配置，支持保存、预览、发布快照和审批详情动态渲染。
- 提供钉钉式流程设计器交互，业务节点配置最终仍转换为 BPMN XML 与节点配置表。
- 发布时做一致性校验，避免表单缺失、流程断线、审批人缺失、条件分支无兜底等无效模板进入已发布状态。
- 保持已有 BPMN XML、Flowable、`biz_process_template`、`biz_process_node_config` 基础模型可复用。

**Non-Goals:**

- 不实现独立流程引擎或替换 Flowable。
- 不实现复杂表单布局设计器，例如栅格布局、子表单、公式字段、跨字段联动。
- 不实现移动端审批表单设计。
- 不实现插件市场式字段扩展机制。
- 不重写所有审批业务页面；优先覆盖通用审批模板和实例详情。

## Decisions

### D1: 表单配置使用 JSON Schema-like 内部结构，继续存储在 `form_config`

选择：定义项目内部表单 schema，存储在 `biz_process_template.form_config`。结构包含 `version`、`fields`、字段基础属性、校验规则和选项配置。

理由：当前表已有 `form_config`，继续使用可以降低迁移成本；内部 schema 比引入第三方表单协议更可控，适合当前审批场景。

备选：新增多张字段配置表。该方案查询和版本快照更复杂，当前字段规模不大，过度设计。

### D2: 表单构建器前端组件化，后端只做 schema 校验和持久化

选择：前端负责拖拽排序、属性面板、预览渲染；后端在保存和发布时校验 schema 完整性。

理由：表单构建是交互密集型能力，放在前端更自然；后端必须保留最终校验，避免绕过 UI 写入非法配置。

备选：后端生成表单 UI 配置。会让展示逻辑和服务层耦合，扩展成本更高。

### D3: 钉钉式设计器作为业务编排层，发布时生成 BPMN XML

选择：设计器维护业务节点模型，保存时同步生成 BPMN XML 和 `biz_process_node_config`。Flowable 仍只消费 BPMN。

```text
业务节点树/图
  -> 节点配置 JSON
  -> BPMN XML
  -> Flowable deploy
```

理由：业务人员不应该直接编辑 BPMN 细节；但 Flowable 部署、运行、任务监听仍然成熟可用。

备选：继续直接使用 bpmn-js 原生画布作为主入口。对业务配置不够友好，条件分支和审批人配置成本高。

### D4: 发布模板创建不可变快照，运行实例绑定发布版本

选择：发布时固化 `published_bpmn_xml`、`form_config` 和节点配置；运行实例读取其 `process_template_id` 对应版本展示表单详情。

理由：审批实例必须可追溯，即使后续创建新版本，历史实例也应按当时发布的表单和流程展示。

备选：实例只绑定 `template_key` 最新版本。会造成历史实例展示错版，审批审计不可接受。

### D5: 条件分支先支持基于表单字段的简单表达式

选择：条件节点支持字段、操作符、值三元组配置，并生成 Flowable 条件表达式。复杂表达式保留高级模式。

理由：覆盖常见审批场景，例如金额、天数、类型分支；同时避免把任意表达式作为默认入口带来的安全和理解成本。

备选：完全开放 UEL 表达式编辑。能力强但风险高，普通管理员难以维护。

## Risks / Trade-offs

- [表单 schema 与历史数据不兼容] → 提供 schema 版本号和兼容解析；旧 JSON 缺字段时按只读简化表单渲染。
- [设计器生成 BPMN 与节点配置不一致] → 保存和发布时统一从同一业务节点模型生成两份产物，避免双写来源。
- [条件表达式生成错误导致流程卡住] → 发布前执行静态校验，条件分支要求至少一个默认分支。
- [动态表单运行时校验不一致] → 前后端共享字段类型和校验规则约定，后端提交审批时再次校验必填和基础类型。
- [一次性范围过大] → 先交付常用字段和常用节点，复杂字段、移动端设计和高级表达式后续扩展。

## Migration Plan

1. 定义 `form_config` schema 版本和字段类型常量。
2. 为旧模板提供兼容解析：无 schema 版本时视为 legacy fields 结构。
3. 新增动态表单构建器与运行时渲染组件。
4. 增强流程设计器业务节点模型和 BPMN 生成逻辑。
5. 后端发布逻辑增加表单和流程一致性校验。
6. 审批实例详情使用模板发布快照动态渲染表单数据。

回滚策略：保留原 BPMN XML 设计入口和原 `form_config` 字段；如果新设计器异常，可临时关闭新入口，已发布模板仍由 Flowable 定义运行。

## Open Questions

- 附件字段是否需要接入独立文件服务，还是先只保存文件 URL 列表。
- 条件分支是否允许跨字段组合条件，首版建议支持 AND 组合，不支持嵌套 OR。
- 抄送节点是否在流程中生成真实 Flowable task，还是继续作为业务抄送记录处理。
